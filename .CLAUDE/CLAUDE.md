# BE AI 작업 규칙

BIUM 백엔드에서 AI에게 개발을 맡길 때 따르는 규칙이다.

작업 전에 이 문서, API 명세서, ERD를 먼저 읽는다.

## 1. 프로젝트 정보

- 프레임워크: Spring Boot
- 인증: Spring Security + JWT, 비밀번호는 BCrypt
- DB: MySQL + JPA
- 예약 작업: @Scheduled (유통기한 이메일 알림)
- 외부 API: Gemini(레시피 추천·영수증 인식), 식약처 식품영양성분DB, JavaMailSender
- 배포: ngrok
- 기준 문서: API 명세서, ERD, 노션 스프린트 계획, 요구사항 목록
- 협업: 기능 단위 브랜치 → Pull Request 리뷰 → main 병합

### 패키지 구조

```
domain/
  auth/       회원가입, 로그인, JWT
  fridge/     냉장고, 공유, 멤버
  ingredient/ 식재료
  recipe/     AI 레시피 추천
  ...
    controller/
    service/
    repository/
    entity/
    dto/
global/
  config/     Security, CORS 등 설정
  exception/  공통 예외 처리
  response/   공통 응답 형식
```

## 2. 기본 규칙

1. **구현 전에 기존 코드를 확인한다.**

   관련 파일, 프로젝트 구조, 사용 중인 라이브러리와 버전, 기존 구현 방식을 먼저 파악한다.

2. **요구사항을 기준으로 판단한다.**

   결과에 큰 영향을 주는 정보가 빠졌으면 질문한다. 사소하고 되돌릴 수 있는 선택은 기존 코드의 관례에 따라 진행하고 필요한 가정을 알린다.

3. **문제 해결에 필요한 범위를 수정한다.**

   버그는 원인을 확인해 수정한다. 요청과 무관한 리팩터링, 파일 이동, 패키지 추가는 피한다.

4. **기존 작업과 일관성을 유지한다.**

   사용자가 수정한 내용을 보존한다. 기존 명명 규칙, 폴더 구조, 오류 처리 방식을 따르고 활용 가능한 코드를 재사용한다.

5. **단순하고 읽기 쉽게 구현한다.**

   현재 요구사항에 필요한 구조를 사용한다. 복잡한 추상화나 사용하지 않는 확장 기능을 추가하지 않는다. 주석은 코드만으로 알기 어려운 이유를 설명할 때 작성한다.

6. **확인한 사실을 바탕으로 작성한다.**

   함수, API, 설정 옵션의 존재와 사용법을 확인한다. 불확실한 부분은 프로젝트 코드나 해당 버전의 공식 문서에서 확인한다.

7. **변경에 맞게 검증한다.**

   변경의 영향에 따라 관련 테스트, 타입 검사, 빌드 등을 선택해 실행한다. 정상 동작과 주요 오류·경계 상황을 확인한다. 실행하지 못한 검증은 이유와 함께 표시한다.

8. **결과를 간결하게 보고한다.**

   무엇을 왜 바꿨는지, 어떻게 검증했는지, 남은 문제가 있는지 설명한다. 실제로 실행하지 않은 테스트를 통과했다고 말하지 않는다.


## 3. 코드 작성 규칙

### 계층 역할

- Controller: 요청을 받고 응답을 돌려준다. 비즈니스 로직을 넣지 않는다.
- Service: 비즈니스 로직과 트랜잭션을 담당한다.
- Repository: DB 조회와 저장만 담당한다.
- Entity를 응답으로 그대로 내보내지 않고 DTO로 바꿔서 반환한다.

### API

- 주소, 요청·응답 형식, 상태 코드는 API 명세서를 따른다.
- 명세를 바꿔야 하면 코드부터 고치지 말고 먼저 알린다. FE가 같은 명세로 개발하고 있다.
- 주소는 복수형 명사로 쓴다. (예: `/api/fridges/{fridgeId}/ingredients`)
- 목록 API가 커질 수 있으면 페이징을 적용한다. (예: 피드)

### 응답과 예외

- 성공·실패 모두 공통 응답 형식으로 반환한다.
- 예외는 공통 예외 처리(`@RestControllerAdvice`)에서 처리하고, 에러 코드와 메시지를 정해진 형식으로 보낸다.
- 상태 코드 기준:
    - 400 잘못된 입력
    - 401 로그인 필요, 토큰 만료
    - 403 권한 없음
    - 404 데이터 없음
    - 409 중복 (예: 이미 가입된 이메일)
    - 500 서버 오류
- 서버 내부 오류 내용(스택 트레이스, SQL)을 응답에 담지 않는다.

### 입력 검증

- 요청 DTO에 `@Valid`와 검증 어노테이션을 사용한다.
- 날짜, 수량처럼 범위가 있는 값은 서버에서도 확인한다.

### DB와 트랜잭션

- 테이블 구조는 ERD를 따른다. 컬럼을 추가·변경하면 ERD도 함께 수정하도록 알린다.
- 여러 데이터를 함께 바꾸는 작업(예: 요리 완료 후 재료 차감)은 하나의 트랜잭션으로 처리한다.
- 목록 조회에서 N+1 쿼리가 생기지 않는지 확인한다.

## 4. 보안 규칙

- 비밀번호는 BCrypt로 암호화해서 저장한다. 원문을 저장하거나 로그에 남기지 않는다.
- JWT 비밀키, DB 비밀번호, Gemini·식약처 API 키, 메일 계정은 환경변수로 관리하고 Git에 올리지 않는다.
- 냉장고·식재료·공유 API는 요청한 사용자가 그 냉장고의 소유자나 멤버인지 서버에서 확인한다.
- 다른 사용자의 id를 요청에 넣어도 접근할 수 없어야 한다.
- 로그인, 회원가입 외의 API는 인증이 필요하다.
- CORS는 프론트 주소만 허용한다.

## 5. 외부 API 규칙

- Gemini, 식약처 API 호출에는 시간 제한을 둔다.
- 실패, 시간 초과, 이상한 응답을 처리하고 로그를 남긴다.
- AI 응답은 그대로 믿지 않고 형식과 값을 검증한 뒤 저장한다.
- 무료 API 한도가 있으니 같은 요청이 반복되지 않게 막고, 영양 정보처럼 바뀌지 않는 값은 저장해서 다시 쓴다.
- 이메일 알림은 같은 알림이 두 번 가지 않게 발송 기록을 남긴다.

## 6. 검증

- 변경 후 `./gradlew test`, `./gradlew build`를 실행한다.
- Service의 핵심 로직에는 테스트를 작성한다. (정상, 예외, 권한 없음)
- API는 Postman이나 테스트 코드로 정상 응답과 오류 응답을 모두 확인한다.
- 실행하지 못한 검증은 보고에 이유와 함께 적는다.

## 7. Git

- 브랜치 이름: `feat/기능명`, `fix/버그명`
- 커밋 메시지: `feat: 회원가입 API 추가`, `fix: 토큰 만료 처리 수정`
- 한 커밋에는 한 가지 변경만 담는다.
- `application.yml`의 비밀값, `.env`는 커밋하지 않는다.
- main에 직접 푸시하지 않고 Pull Request로 합친다.

## 8. 요구사항 작성 형식 (스프린트 시작 때 작성)

```
### 기능 이름
- 입력: 요청 주소, 요청 값
- 출력: 응답 값, 상태 코드
- 예외 상황: 잘못된 입력, 권한 없음, 데이터 없음, 외부 API 실패 등과 각각의 처리 방법
- 레퍼런스: API 명세, ERD, 참고할 기존 코드, 공식 문서
```

### 예시: 회원가입 API

- 입력: `POST /api/auth/signup` / 이메일, 비밀번호
- 출력: 201, 가입한 사용자 id
- 예외 상황:
    - 이미 가입된 이메일 → 409
    - 이메일 형식 오류, 비밀번호 조건 미달 → 400
- 레퍼런스: API 명세서, Spring Security 공식 문서
